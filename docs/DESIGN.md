## 1. 何を作るか

**gera は、AI が生成した Markdown 文書を読むためのデスクトップビューアである。編集機能も持つが、それは従である。**

本人の言（逐語）:

> 一番のユースケースが「AI が書いた Markdown 文書を読む」なので、**ほとんどビューアーで、おまけで編集機能がある**、ぐらいの立ち位置

> **閲覧モードが一番このツールで使いたい機能**

> ただしおまけの部分はビュアーと**対応がつくほうがよい**

**発案者は友人である。**本人の言:「AI 文書を読みやすくしたいというアイデアは実は友人がいい出したこと」。

**名前**: `gera` はゲラ（校正刷り）から取った。組版を終えて刷り上がり、これから読み合わせて赤を入れる紙のことである。AI の出力はゲラである——すでに形になっていて、体裁も整っているが、そのままでは出せない。本人が本日「**今もなおピッタリの名前**」と確認済み。変更しない。

## 4. 優先順位

## 5. 実測

**本節の数値は本人の開発機（Ubuntu 24.04 / GNOME Wayland / 16 コア / 128GB / 1920×1080 @ 60Hz）で計測したものである。測定条件を各項に明記する。**日付の断りがないものは 2026-09-02 の計測である。

**読む前に 5-8 を読むこと。**2026-09-03 に**計測の道具そのものが数値を歪めていたことが三度判明した**。とくに `GDK_BACKEND=x11` の計測ハーネスを通した値は**実環境より約 560 ms 過大**である。どの数値がどの条件のものかは各項に明記した。

**実環境（ネイティブ Wayland）の起動から描画完了までの値は 5-11 にある。**本節の他の項に現れる描画時間は、断りのない限り x11 ハーネスの値であり**過大である**。**基点も違うので、単純に比べてはならない**（5-11）。

### 5-1. 起動速度

**測定手法**: `WAYLAND_DEBUG=1` で Wayland プロトコルの流れを直接観測し、`xdg_surface.get_toplevel`（ウィンドウ生成）と、そのトップレベル面への最初の `wl_surface.attach` + `commit`（**最初のピクセルが存在する瞬間。コンポジタはこれ以前にウィンドウを表示できない**）を記録した。3 つのアプリに**同じ文書**（497 行 / 約 20,000 字）を与え、同一の計器・同一の手順で測定。ウォーム起動 n=6 の中央値。

| | ウィンドウ生成 | **最初の描画** | 文書読み込み完了 |
|---|---|---|---|
| **gera** | 0.068 s | **0.274 s**（0.272–0.280） | 0.565 s |
| **Zed** | 0.126 s | **0.444 s**（0.401–0.459） | 0.459 s |
| VS Code | 0.336 s | 0.707 s | 1.025 s |

**gera は Zed より速く画面を出す**（Zed の約 6 割の時間）。文書読み込み完了では Zed が約 0.1 秒速く、**ほぼ互角**である。**VS Code は倍以上かかる。**

**コールド起動**（n=5、`posix_fadvise` でページキャッシュを追い出して測定）: gera 1.853 s / Zed 3.832 s。**ただしこの比較は gera に有利に歪んでいる。**本人が起動していた gera インスタンスがバイナリの 43% をキャッシュに固定しており、追い出せたのは 57% のみであった（Zed は完全にコールド）。またバイナリサイズが gera 14.8MB 対 Zed 459MB で、差の大半は読み込み量による。**参考値として扱うこと。**

### 5-2. スクロールの滑らかさ

**測定手法**: `/dev/uinput` の仮想マウスで高解像度ホイールイベントを 125Hz で 3 秒間注入した（アプリの描画能力を上回る速度なので、律速はアプリ側にある）。フレーム間隔はトップレベルの commit から測った。各 3 回。

| | 中央値 | p95 | vsync 1.5 倍以内 |
|---|---|---|---|
| **gera** | 16.5 ms | 17.9–18.4 ms | **98.4–99.5%** |
| **Zed** | 16.5–16.6 ms | 18.1–22.2 ms | 96.0–99.5% |

**両者とも 60fps（vsync 16.67ms）に貼り付いており、フレームの出し方において gera は Zed に劣らない。**

**この表の gera の値には訂正が要る**（2026-09-03）。**測定当時の gera はアイドル中も 16.6 ms 間隔でフレームを出し続けており**（下記の二つ目の問題。原因と修正は 5-10）、**スクロール中の計数にその等間隔のフレームが混ざっていた。**つまり **98.4–99.5% という揃い方は、水増しされていた可能性がある。**

**5-10 の修正後に、同じ手法（`/dev/uinput` から 125Hz で 3 秒、トップレベルの commit 間隔）で測り直した値**:

| | 中央値 | p95 | vsync 1.5 倍以内 | 窓内の commit 数 |
|---|---|---|---|---|
| 修正前（同一ハーネス、n=4） | 16.5–16.6 ms | 18.3–19.2 ms | 97.1% | 172–174 |
| **修正後（n=16）** | 16.5–16.6 ms | 17.7–19.9 ms | **95.9–98.3%** | 171–175 |

**これは回帰ではない。**修正前を**同じハーネスで**測り直しても 97.1% であり、上表の 98.4–99.5% との差は**測定時の負荷と、上記の水増しの両方**による。**注入が届いていた証拠**として、全ランで `wl_pointer.axis` を 62 件受信している——これは下記の「gera は 62 個の粗いノッチ」と一致する。

**「フレームの出し方において Zed に劣らない」という結論は維持する。**ただし**その根拠となる数字の精度は、当初の記載より低く見積もること。**測り直す余地は残っている（第 15 節）。

**同じ測定で 2 つの問題が判明した。どちらも実測で確認済みであり、課題として残す。**

- **gera は高解像度スクロールを受け取れていない。**同じスクロール距離に対して Zed が 375 個の細かいイベントを受けるのに対し、gera は 62 個の粗いノッチしか受けない。**原因は GTK3/WebKitGTK の `wl_seat` バージョンの制約である。**フレーム落ちは起きないが、1 フレームあたりの移動量が約 6 倍粗い。**2026-09-03 に本人が release ビルドを実機で操作し、カクつきとしては感じられないことを確認した**（5-9）。**ただし制約そのものは残っている**——本人の言「ぬるぬる動く」というレベルではない、はこの粗さに対応している可能性が高い
- **gera はアイドル中も 60fps で描画し続けている。**入力のない 3 秒間に 130 フレームを出した（Zed は 2 フレーム＝カーソル点滅のみ）。**これは滑らかさの問題ではなく、GPU と電力を無駄に消費するバグである。**閲覧モードに切り替えた直後から始まっており、作りかけの閲覧モードのコードが原因と見られた——**この見立ては外れていた。**原因は gera のコードではなく WebKitGTK の既定のスクロールバーであり、**2026-09-03 に決着した**（5-10、第 12 節）

**打鍵の遅延は測定していない。**gera がアイドル時も毎 vsync フレームを出しているため、「キー入力から次のフレームまで」を測ると構造上つねに 16ms 以下となり、意味のない数字になる。本人がこの項目を優先順位の最下位に置いていることもあり、見送った。**アイドル描画が止まった以上（5-10）、この障害は無くなった。測る余地が開いたが、まだ測っていない**（第 15 節）。

### 5-4. 数式を含む文書の描画（最重要）

**測定対象**: 本人の実際の文書 `linear-pde-stages/decide-0830/Phase2/findings.md`——**2,838 行 / 212,822 バイト / 数式 2,204 個**（`$$…$$` 175、`$…$` 2,029）。

**測定環境**: WebKitGTK 2.52 系の `MiniBrowser`（**Tauri が Linux で使うエンジンそのもの**）。すべてのアセットをローカルから配信（CDN 不使用）。`document.fonts.ready` 待ちを含む。n=5 の中央値。

| 構成 | ウォーム合計 | **コールド（初回）** |
|---|---|---|
| **KaTeX（素直に全部 `innerHTML`）** | **1,156 ms** | **3,079 ms** |
| MathJax v3 CHTML | 1,255 ms | 2,221 ms |
| 数式なしの文書（499 行、対照） | **64 ms** | 144 ms |

**数式が描画時間を 18 倍に押し上げている。そして初回 3.1 秒は、本人が VS Code に感じている「数秒」と同じオーダーである。「Tauri だから速い」はここでは成り立たない。**

**時間の内訳**（KaTeX × WebKitGTK ウォーム）: レイアウト＋ペイント 951 ms（**82%**）、HTML 生成 93 ms（8%）、`innerHTML` 75 ms（6.5%）。**コールドではフォント読み込みが支配的**（初回のみ約 +1.8 秒）。

**対策の効果**（同条件、3 回中央値）:

| 方式 | 初回描画 | 全挿入完了 |
|---|---|---|
| 一括 `innerHTML` | 1,028 ms | 1,028 ms |
| **`content-visibility: auto` を付与** | **449 ms** | **449 ms** |
| 先頭 60 ノードを先に挿入 → 残りを 200 ずつ | **177 ms** | 1,108 ms |

**`content-visibility: auto` は CSS 1 行で描画時間を半分以下にし、しかも全挿入完了までを短縮する。**分割挿入は初回描画こそ速いが、完了は伸びる。**したがって `content-visibility` を先に入れ、それでも足りなければ分割を足す。**

**この対策は初版の必須要件である。**入れなければ、本人の主要な文書を開くたびに数秒待たされ、企画の出発点である「VS Code は重い」（第 2 節）を解決できない。

**段階的な描画の効果**（2026-09-03、実装済みの閲覧モードで計測。`content-visibility: auto` は両条件とも有効）:

| 文書 | 一括で組む | **段階的（先頭 8 ブロック）** |
|---|---|---|
| findings.md（2,838 行 / 2,204 数式） | 1,300 ms | **629 ms** |
| rejected.md（956 行） | 867 ms | **662 ms** |

**先頭何ブロックを先に組むかは実測で決めた。**0 は `IntersectionObserver` の初回配送が一巡増えるぶん遅く、20 以上は画面外まで組むぶん遅い。**二つの文書とも 8 が最小だった**（20 は 695 / 689 ms、40 は 725 / 724 ms）。**残りは `IntersectionObserver` が近づいたブロックから埋める。**

**この表の値には但し書きが要る。**計測は `GDK_BACKEND=x11` のハーネスによるもので、**実環境より約 560 ms 過大である**（5-8）。**ただし削減幅は同一条件同士の比較なので有効である**——1,300 → 629 ms の 671 ms も、867 → 662 ms の 205 ms も、ハーネスの上乗せは両側に等しく載っているため差し引きで消える。

**実環境の値は 5-11 にある。**そちらは `findings.md` で 0.778 秒である。**この 629 ms と並べてはならない**——629 ms は**x11 ハーネスで、JS の起動を基点に**測った値であり、0.778 秒は**ネイティブ Wayland で、プロセスの `exec` を基点に**測った値である。**基点が違う**（5-11）。

### 5-5. KaTeX と MathJax の比較（通説の訂正）

| | 変換（Node、CPU のみ） | レイアウト | 合計（WebKitGTK） |
|---|---|---|---|
| KaTeX | 137.6 ms | 951 ms | **1,156 ms** |
| MathJax v3 CHTML | 853.7 ms（**6.2 倍**） | 352 ms | **1,255 ms** |

**「MathJax は KaTeX より遅い」は、変換段階に限れば正しいが、文書全体の描画時間では成り立たない。**MathJax CHTML の DOM はレイアウトが 2.7 倍速いため、**end-to-end の差はわずか 9%** である（Chrome でも 737 対 1,000 ms）。**速度だけを理由に MathJax を却下するのは、数字に照らして誤りである。**

**それでも KaTeX を採る。理由は速度ではない。**

1. **MathJax の利点（`\label` / `\eqref` の解決と自動採番）を、本人の文書は使っていない。**実測で対象 3 文書とも `\label` 0 個・`\eqref` 0 個・`\ref` 0 個・`\tag` 0 個。**対価が空振りする**
2. **バンドルが 0.9 MB → 3.8 MB に膨らむ。**起動速度が第一優先である（第 4 節）
3. **MathJax は同じ文書を 2 回描くと `Label 'xxx' multiply defined` でエラーを出す**（タグ状態が document インスタンスに残るため。3 連続レンダーで再現確認済み）。**局所編集で再描画を繰り返す設計（第 9 節）では必ず踏む**
4. **KaTeX のコストはレイアウトに集中しており、`content-visibility` 1 行が効く**（5-4）。**MathJax のコストは JS 変換なので同じ手が使えず、Worker 化かキャッシュが必要になる**

**将来 `\eqref` を実際に使う文書が現れたら、MathJax の再検討は妥当である。**速度差が 9% しかない以上、そのときは機能で選んでよい。**この余地は開けておく。**

**採用するプラグインは `@vscode/markdown-it-katex`** である。Microsoft 保守であり、**VS Code の Markdown Preview が実際に使っている当のもの**なので、本人の基準「VS Code のプラグインぐらいのサポートでいい」（第 11 節・規則 1）と正確に一致する。`markdown-it-katex` は 2017 年で更新停止しており使わない。

**`\label` の扱い**: KaTeX は `\label` を解釈できず、**該当する数式は消えて英語のエラー文が本文に出る**（`ParseError: KaTeX parse error: Undefined control sequence: \label`、`class="katex-error"`、赤くならず通常の本文色）。**ただし本人の数式文書に `\label` は 1 個も入っていない。**ツリー全体で見つかった 1,443 箇所は、200 個以上に複製された `STYLE.md` テンプレートに 7 個ずつ含まれるもので、数式本文ではない。**したがって `\label` の前処理除去は「必要な処置」ではなく「ほぼ無料の保険」である**（215KB に対する正規表現置換が中央値 0.035 ms）。**入れるが、位置づけはこれである。**

### 5-6. 遅延読み込みの価値

**測定**: KaTeX のアセット読み込みのみ（コールドページ、3 回）。JS 14–16 ms ＋ CSS 2 ms ＋ 初回 1 式描画 66–67 ms ＋ `fonts.ready` 14–17 ms = **合計 97–101 ms**。

同梱サイズ: `katex.min.js` 272KB ＋ CSS 24KB ＋ フォント 1.2MB。

**判断: 遅延読み込みの価値は「あるが小さい」。**数式のない文書（64 ms で描ける。5-4）に対して 100 ms の上乗せは相対的には大きいが、絶対値では 0.1 秒である。**実装が複雑になるなら見送ってよい水準であり、必須ではない。**

### 5-7. 本人の Markdown 資産

### 5-10. アイドル時 60fps 描画の原因と修正（2026-09-03）

**5-2 が残した「アイドル中も 60fps で描画し続ける」バグは決着した**（コミット `c65f280`、第 12 節）。**実害は二つあった。**第一に**電力と GPU を無駄に食う。**第二に**「フレームが止まったら描画完了」という判定が使えない**ため、**ネイティブ Wayland での描画完了時刻が測れなかった**（5-11 で測れるようになった）。

- **決め手は損傷領域だった。**毎フレーム変わっていたのは**右端 21px の帯だけ**で、本文は 1 ピクセルも動いていない。「何が描き直されているか」を見るまで、犯人は本文の側にあると思い込んでいた

**事前の仮説はすべて外れた。次に同じ調査をする者のために残す。**

- **最有力とされていたのは `content-visibility` × `IntersectionObserver` の相互発火だった。**実際には `fillBlock` が `pending` からの削除と `unobserve` の両方を行っており、**二度目は弾かれる**
- **`hr` だけの文書**（`content-visibility: visible`）**でも同じ数字が出た。**`content-visibility` は無関係である
- **`rAF` ループも `setInterval` も CSS アニメーションも `will-change` も、コードに存在しない**

**修正**: **`::-webkit-scrollbar` を一つでも定義すると、WebKit は OS 側の重ね置きをやめて CSS で描くスクロールバーに切り替える。こちらは薄くなるアニメーションを持たないので、静止していればフレームが出ない。**定義は `src/style.css` にある。

**代償は幅 10px が常に見えることである。**消すこともできるが、**2,838 行を通しで読むのが主用途である以上**（第 2 節）、**いまどこを読んでいるか分からなくなるほうが失うものが大きい。**

**編集モードにも同じバグがあった**（CodeMirror のスクロール面）。**したがって規則は `*` に当てている**——片方だけ直すと、残ったほうが同じ費用を払い続ける。

**実測**（ネイティブ Wayland、`WAYLAND_DEBUG=1` でトップレベル面の `attach`＋`commit` を計数）:

| 条件 | 修正前 | 修正後 |
|---|---|---|
| 閲覧・`docs/DESIGN.md` | 3 秒に 179 | 起動 0.54 秒以降 **0** |
| 閲覧・`findings.md` | 3 秒に 179 | 起動 0.75 秒以降 **0** |
| 編集モード | 切替直後に 3.010 秒で 182 フレーム | 3 秒に 10（**カーソル点滅のみ**） |
| スクロール 1 回あたりの追加 | 1.0 秒に 62 ＋ 3.0 秒に 181 フレーム | 無し |

**回帰を一つ始末した。**`.gera-math` は `overflow-x` のみを指定していたが、**CSS の規定により `overflow-y` は `visible` のままではいられず `auto` に落ちる。**そのため背の高い別行立て数式（`\int` のような記号）の右脇に**縦のスクロールバーが出た。**`overflow-y: hidden` を明示して解消した——**見えるものは変わらない**（先頭にある箱と、切り落とした箱は同じピクセルを出す）。変わるのは送れるかどうかだけである。

## 6. 技術選定

| 領域 | 選定 | 根拠 |
|---|---|---|
| アプリ基盤 | **Tauri 2** | 実測で起動が Zed より速く、スクロールも互角（5-1、5-2）。バイナリ 4.7MB（5-3）。第一優先の速度に直接効く |
| エディタコア | **CodeMirror 6** | カーソル・選択・アンドゥ・IME・折り返しの自作は数ヶ月かかる。可視行のみ DOM 化する |
| フロントエンド | **素の TypeScript + Vite** | 画面は本文一枚、DOM は CodeMirror が所有、状態は数個。React は突き合わせる木がなく、CodeMirror の命令的 DOM と摩擦を生むだけである |
| 閲覧モードの変換 | **`markdown-it` ＋ DOMPurify** | 下記 |
| 数式 | **KaTeX**（`@vscode/markdown-it-katex`） | 5-5 の 4 点 |
| Rust 側の責務 | ファイル入出力、ダイアログ、ウィンドウ状態、コマンドライン引数 | 呼び出しは `src/host.ts` に集約する |

**Tauri を採るという判断は 2026-09-03 に確定した。**性能が足りなければ**Tauri を降ろしてネイティブ（GPU 描画）へ寄せる**案が検討されていたが、**本人の実機確認で「爆速です。OK」という判定が出た**（5-9）。**寄せる必要はなかった。**これが第 6 節の技術選定を支える最大の根拠である——**実測だけでなく、基準を出した本人自身が満たされたと言った。**

**`markdown-it` には `markdown-it-cjk-friendly` を併用する。**CommonMark の左右フランキング規則では、**語間に空白のない日本語で `**…**` が装飾として認識されないことがある**（第 12 節）。**AI が生成する日本語文書で頻繁に踏むため、必須である。**

**`markdown-it` を採り、`@lezer/markdown`（CodeMirror が内部で使う）を流用しない理由**: `@lezer/markdown` は Lezer 構文木を出すだけで **HTML 描画器を持たない。**自前で書けば、全ノード種の走査・インライン装飾・実体参照エスケープ・リンク解決・リストの tight/loose 判定をすべて書くことになる。**なお「変換器を一本化すれば両モードの表示が一致する」という論法は使わない**——両モードの対応づけは**行番号**（`markdown-it` の `token.map` から `data-line` 属性を出す）で取れるため、一本化の理由にならない。

**`markdown-it` は `html: true` で使い、描画前に必ず DOMPurify を通す。**`html: false` だと AI 出力に頻出する `<details>` や `<br>` が生テキストで出てしまい、査読の役に立たない。**生の HTML を通す以上、sanitize は必須である。**その理由と、DOMPurify の使い方（許可リスト方式・`data-line` の明示的な許可）、および sanitize だけに頼らない理由は第 7 節にまとめた。

**抽象化の層を設けない。**実装が一つしかない層は、それ自体が概念を一つ増やす（第 4 節の第二優先に反する）。乗り換えが必要になったとき書き直す対象が `src/host.ts` だけだと分かっていれば足りる。

## 7. 安全性

本人の言（逐語）:

> **セキュリティについてはどう考えればよいでしょう？雑につくると任意コード実行が可能になってしまわないか心配です。**

**この懸念は妥当である。**gera は他人が書いた文書を開くソフトウェアであり、以下に示すとおり、素朴に作れば**永続的な任意コード実行に到達する経路が実在する。**

### 7-1. 脅威

**gera は、自分が書いたのではない Markdown を開く。**AI が生成したもの、友人から受け取ったもの、web から落としたもの。**開く文書が悪意を持っている場合を想定しなければならない。**これは gera の中心的な用途（第 1 節）から直接出てくる要請であって、一般論ではない。

**攻撃は次の段階を踏んで成立する。**

1. 悪意ある Markdown が `markdown-it`（`html: true`。第 6 節）を通り、**生の HTML が出力に残る**
2. その HTML が webview の DOM に入る
3. `<script>` や `onerror=` のような形で **JavaScript が動く**
4. webview には `window.__TAURI_INTERNALS__` があるため、そこから **`invoke("write_file", …)` を呼べる**
5. `~/.bashrc` や `~/.config/autostart/` に書き込まれる = **永続的な任意コード実行**

**この筋道は現在の構成で実際に成立する。**「たぶん大丈夫」ではない。**成立しないのは 7-2 の防御が効いているからであって、設計が安全だからではない。**

### 7-2. いま効いている防御——CSP

`src-tauri/tauri.conf.json` の現在の設定（実際の値）:

```
default-src 'self'
style-src   'self' 'unsafe-inline'
img-src     'self' asset: data: blob:
font-src    'self' data:
connect-src 'self' ipc: http://ipc.localhost
object-src  'none'
frame-src   'none'
```

- **`default-src 'self'` が `script-src` を兼ねるため、注入されたインラインスクリプト・イベントハンドラ属性・`javascript:` URL はいずれも実行されない。**7-1 の段階 3 がここで止まる。**これが最大の防御である**
- **`img-src` と `connect-src` が外部を許していないため、仮にスクリプトが動いても情報を外へ送れない。**画像ビーコンも `fetch` も塞がっている
- `style-src` の `'unsafe-inline'` は CodeMirror が必要とする。**インラインスタイルから JavaScript は実行できない**（現代のブラウザに `expression()` はない）ため、**これは許容できる**

### 7-3. いま空いている穴——Rust 側の権限が無制限

現在の Rust コマンドの署名（実際のもの）:

```rust
fn read_file(path: String) -> Result<String, String>
fn write_file(path: String, contents: String) -> Result<(), String>
```

**`path` が任意である。**呼び出し元がどのパスを渡しても、Rust 側は素通しで読み書きする。

- **CSP は設定値であり、将来ゆるめられうる。**たとえば何かの都合で `script-src` に `'unsafe-inline'` を足した瞬間に、7-2 の防御は崩れる
- **そのとき `write_file` が無制限だと、即座に永続的な RCE になる。**7-1 の段階 4–5 を止めるものが何も無い
- **サニタイズと CSP は「危険な入力を除去する」防御であり、いずれも過去に回避例がある。**DOMPurify も CSP も例外ではない。**一枚に賭けてよい種類の防御ではない**

### 7-4. 方針——能力を絞る

**最も深い防御は、危険な入力を除去することではなく、危ないことがそもそもできない状態を作ることである。存在しない権限は回避できない。**

**以下は初版の要件である。**

**(a) Rust 側に「許可済みパスの集合」を持たせる**

- 集合に入るのは、**利用者が自分の手で指し示したパスだけ**である——ファイルを開くダイアログで選んだ、保存ダイアログで選んだ、コマンドライン引数で渡された（9-5）
- **`read_file` と `write_file` は、集合にないパスを拒否する**
- **これにより、webview が完全に乗っ取られても被害が閉じる。**書けるのは利用者自身が選んだファイルだけであり、`~/.bashrc` にも `~/.ssh` にも届かない
- 実装は `Mutex<HashSet<PathBuf>>` 相当で数十行である。**パスは正規化してから比較すること**——`..` やシンボリックリンクによる回避を防ぐため、`std::fs::canonicalize` を通した結果を突き合わせる

**(b) DOMPurify は許可リスト方式で使う**

必要なタグ・属性だけを明示的に通す。**拒否リスト方式より堅い**——知らない攻撃面が既定で閉じている側に倒れるためである。**`data-line` 属性（第 6 節の行番号対応に使う）は明示的に許可する必要がある。**

**(c) KaTeX は `trust: false`（既定のまま）**

`\href{javascript:...}` と `\includegraphics` を封じるためである。**既定値なので、明示的に変えないこと**が要件になる。

**(d) リンクは `http` と `https` のスキームだけを OS に渡す**

外部 URL はブラウザへ渡す設計である（9-1）。**`file:` や独自スキームは拒否する。**

### 7-5. 位置づけ

**7-4 の対策は初版の要件であって、後回しにしない。**理由は二つある。**第一に、穴を開けたまま作ってから塞ぐのは、塞ぎ忘れる。**第二に、**とくに (a) は、`write_file` を実装した後から足すより、最初から集合を通す形で書くほうが安い。**

**ただし、これは「絶対に安全」を主張するものではない。**7-4 は多層防御であり、**一層が破られても次の層が残る**という設計である。CSP が破られても書ける先が限られ、許可済みパス集合が破られても CSP が実行を止める。**どの一層も、単独では安全を保証しない。**

**判断とその理由:**

- **記法記号は落とさず、生の Markdown を検索する。**`**強調**` を探せば `**` にも当たる。それでもこちらを採る理由は三つある。**第一に、編集モードで見えているのはこの文字列そのものであり、両モードの件数が食い違わない**（両モードで同じキーが同じ意味を持つことが要件である）。**第二に、記法を落とした本文を別に作ると、その位置から元の行へ戻す対応表が要る。表がずれれば飛び先が狂い、しかもずれても気付けない**（静かに間違うものを増やさない。5-8 の教訓）。**第三に、打った文字がファイルの中にあれば当たる、という規則は grep と同じで、説明が要らない**（第 4 節の第二優先）。**失うのは記法をまたぐ語だけである**（`**強調**され` の「強調され」など）
- **全角半角・かなの同一視はしない。**`NFKC` のような正規化は**文字数を変える**（`ﾊﾞ` の 2 字が `バ` の 1 字になる）ため、**畳んだ文字列で見つけた位置が元の本文と対応しなくなり、飛び先も強調も狂う。**対応表を持てば直せるが、検索一つに持たせる仕掛けとしては重すぎる（第 4 節の第二優先）。**畳むのは大文字小文字だけである**
- **強調は CSS Custom Highlight API（`::highlight()`）を使い、本文の DOM を書き換えない。**`<mark>` で包むと、`data-line` の対応づけ（第 6 節）も `renderFragment` によるブロックの差し替え（局所編集。9-3）も、**包んだぶんだけ形が変わって壊れる。強調は見た目の層だけで完結させる。****WebKitGTK 2.52 で使えることを実機で確認した。**API が無い実装では強調だけを諦める——飛ぶことは成立するので、道具として死にはしない

**色を付けるのは、いま画面に入っているブロックだけである。**これは節約ではなく、**そうしないと壊れるからである**（5-12。画面外のブロックに作ったレンジは、無関係な段落の上に帯として塗られる）。当たりを含むブロックを `IntersectionObserver` で監視し、出入りに合わせて塗り直す。**副作用として、スクロールで新しく画面に入ってきた当たりにも、その場で色が付く。**

**起動時の初期チャンクは +0.57kB**（442.63 → 443.20 kB）。**検索の UI は別チャンク**（`find.js` 3.88 kB ＋ `find.css` 0.84 kB）**で、`Mod+F` を押すまで読まれない**——アウトラインと同じ形である（第 4 節）。

**既知の制限**:

- **記法をまたぐ語には当たらない**（上記の一つ目の判断の代償）
- **編集モードでは、現在の当たりを CodeMirror の選択範囲で示すのみで、他の当たりに色は付かない。****CodeMirror は画面外の行を DOM に持たない**ため、レンジを作っても保たないからである

**サイズは、基準と倍率を別の CSS 変数に分けて実装した。**利用者 CSS が決めるのは**基準**（`--font-size-view` / `--font-size-edit`）で、キーボードが触るのは**倍率**（`--font-scale`）である。実際の指定は `calc(var(--font-size-view) * var(--font-scale))` の形をとる。

- **分けた理由は、`Mod 0` の戻り先である。**一つの `font-size` に押し込むと、`Mod 0` は**利用者が CSS で決めた大きさを消す**操作になる。分けてあれば、戻るのは倍率だけであり、**利用者の決めた基準はそのまま残る**
- **基準が閲覧 17px・編集 16px と別々なのは、書体が違うからである**（明朝とゴシックで字面が違う）。片方に揃えるとどちらかの版面が崩れる
- **版面の他の寸法はすべて `em` の相対指定なので、基準が動けば全体が比例して動く。**`contain-intrinsic-size`（5-4）も `em` で置いてある——**基準と倍率のどちらが動いても推定が付いてくるようにするため**である
- 利用者向けの説明は `docs/CSS.md` に書いた

**読み込み機構**（2026-09-04、コミット `2f287f7`）:

### 9-6. 外部からの書き換えへの追随

Claude Code 等が、gera で開いているファイルを書き換える場面は頻繁に起きる。**規則は「常に知らせるだけ。読み直すかは人が決める」である**（2026-09-04、本人との相談で決定）。

- 変更を検知したら**知らせるだけ**で、**本文は書き換えない。**未保存の変更の有無で分岐しない
- **読み直しは `Mod+R` である。**ブラウザと同じキーなので、**覚えるべき概念が増えない**（第 4 節の第二優先）
- **実装済み**（2026-09-04、コミット `be03e76`。第 12 節、第 14 節の順序 9）。**これで初版の要件が揃った**——残る局所編集（9-3）は要件から外れている。実装の要点は下記「実装の要点」にある

**採る形はブラウザと同じ作法である。**本人の言:

> はい、読み直すかは人が決める、でいいです。**ブラウザと同じですね。**

**(a) `Mod+R` は全部を置き換える一手だけとする。ブロック単位の差し替えにしない。**

**理由は三つある。**

1. **ブロック単位にすると「何と何を突き合わせるか」という選択肢が生まれる。**「前回読んだファイル」と「新しいファイル」を突き合わせる実装は自然に書けてしまうが、**それは読み直しではなく併合であり、`Mod+R` の意味が変わる**
2. **差分ビューが無いので、どこが自分のでどこが相手のかを見せられない**（第 10 節）。**見せずに混ぜるのは危険である**
3. **仕掛けを持った時点で「どのブロックが自分のか」という問いが立つ。**利用者が考えることが増える（第 4 節の第二優先）

**3 は本人の指摘でもある**（逐語）:

> ブロック単位だと「どこまでが未保存の範囲か」「今回の編集の最終保存ファイルとの差分はなにか」を考える必要があって、**ユーザーに分かりづらいかもしれませんね。**

**代償は払う。**全体を描き直すので**約 0.4 秒かかり、一瞬ちらつく**（5-11 の描画時間から見積もった値である）。**`Mod+R` は利用者が明示的に押した操作なので、この代償は払ってよい。**黙って走るものなら話は別である。**読んでいた場所は行番号で保つ**（`data-line`。第 6 節。字の大きさを変えたときや利用者 CSS を読み直したときと同じ手段である）。

**(b) 保存の衝突——外部で書き換わったファイルへの `Mod+S` は拒否する。**

**それまでの実装は黙って上書きしていた。**相手の変更が消えたことに、**誰も気づかない。**本人の指摘:

> 編集中に元のファイルが変更されているときに `Mod+S` を押したときの仕様もちゃんと詰めないとだめですね。

**採る形**——保存の直前に、**読み込んだときの内容といまディスクにある内容をハッシュで突き合わせる。****`mtime` は使わない**——内容が同じでも動くため、変わっていないファイルで拒否が出る。食い違っていたら**保存を拒否し、出口を三つ案内する。三つとも既存のキーで済む**（新しい概念を増やさない。第 4 節の第二優先）。

| | 意味 | キー |
|---|---|---|
| **相手のを取る** | 自分の編集を捨てて読み直す | `Mod+R` |
| **両方残す** | 別名で保存する | `Mod+Shift+S` |
| **自分のを残す** | `Mod+Shift+S` で**同じファイル名を選ぶ。**OS のダイアログが「置き換えますか」と聞く | `Mod+Shift+S` |

**上書き専用のキーを作らない。**「もう一度 `Mod+S` を押せば上書き」という形にすると、**`Ctrl+S` を癖で二度押す人がいるので、データが消える。**三つ目の出口を `Mod+Shift+S` に寄せてあるのはこのためで、**OS のダイアログが「置き換えますか」と一度聞く**ぶん、二度押しでは通り抜けられない。

**(c) 検知は、ウィンドウがフォーカスを得たときに行う。ポーリングもファイル監視もしない。**

**理由は三つある。**

1. **利用者が Claude Code で作業して gera に戻ってくる瞬間が、まさにそのときである。**知らせたい場面と、検知の契機が一致している
2. **常時動く仕組みを持たない。****アイドル時に 60fps で描き続けるバグを直したばかりであり**（5-10）、**ここでポーリングのループを足すのは筋が悪い。**静止していればフレームが出ない、という状態を守る
3. **ファイル監視は依存と常駐スレッドが増える。**それで得られるのは「**フォーカスを持ったまま**変更に気づける」ことだけであり、**その場面は稀である**

**`Mod+S` の直前にも必ず調べる。**フォーカスを持ったまま外部が書き換えた場合を、**保存の瞬間に捕まえるため**である。(b) の突き合わせがそのまま検知を兼ねる。

**(d) 未保存の編集があるときの `Mod+R` は、一度目で止めて押し直しを求める**（2026-09-04）。

**この形しか残らなかった。確認のダイアログを持っていない**（第 9 節。gera は問い返す窓を作らない）、**黙って捨てるのは本節の規則が禁じている**、**新しいキーも増やせない**（第 4 節の第二優先）。**消去法で「押し直しを求める」だけが残った。**一度目は帯で警告して止め、**5 秒以内の二度目で実行する。**帯には**逃げ道も併記する**——「残したいときは `Mod+Shift+S` で別名に保存してください」。**拒否だけを伝えて先を示さないのは、(b) の三つの出口と同じ理由でしない。**

**受付の期限は、帯の寿命（5 秒）と同じにした。画面に出ている警告と、受け付けている状態を一致させるためである。**期限が帯より長いと、**何も表示されていない画面で押した `Mod+R` が本文を捨てる。**

**(b) の「上書き専用のキーを作らない」理屈は、ここには当てはまらない。**`Ctrl+S` は癖で二度押す人がいるので `Mod+S` の二度押しは危険だが、**`Mod+R` は連打する綴りではない。**同じ「二度押し」を (b) では退け (d) では採ったのは、**この非対称性による。**

**実装の要点**（2026-09-04、コミット `be03e76`）:

**検知の契機は二つだけである**——**ウィンドウがフォーカスを得たとき**と、**`Mod+S` の直前**。設計どおり、**ポーリングもファイル監視も持っていない**（(c)）。**フォーカスは DOM の `focus` 事象で拾い、Tauri のウィンドウ事象を購読しない。それで足りたので、capability（`src-tauri/capabilities/default.json`）を変更していない**——権限を増やさずに済んだ。

**知らせるのは、食い違いを見つけた最初の一度だけである。**フォーカスのたびに帯を出し直すと、読み直すまで毎回出ることになって**うるさい。**読み直したときと、保存できたときに倒す。

**指紋の取得そのものが失敗したとき**（ファイルが消された・権限が変わった）**は、console にだけ出して帯を出さない。**これは利用者が起こした操作への応答ではないので、**画面を触っていないのに文字が出るのは筋が悪い。**保存しようとすればそのとき分かる——(b) の突き合わせは、**読めないファイルを食い違い扱いにする**（消されているのに黙って作り直すと、消したという相手の操作を取り消すことになる）。

**指紋は内容のハッシュである。**FNV-1a 64bit にバイト長を添えた文字列（`<長さ>-<16 進 16 桁>`）で、**新しい依存を足していない。暗号学的ハッシュにしなかったのは、ここで守っているのが「利用者が気づかないうちに他人の変更を消す」経路であって、攻撃者ではないからである**——**ファイルを書ける相手は、指紋を合わせるまでもなく好きに書ける。**したがって衝突困難性は要らず、偶然の衝突が実質起きなければ足りる。**`touch` で mtime だけを動かしても偽の知らせが出ないことを、実機で確認した**——内容で見ていることの効果である（(b)）。

**型で穴を塞いだ点が二つある。**

1. **`read_file` の戻り値を `{ text, digest }` にした。**指紋を別の口（`file_digest` だけ）に置くと、「**読んだが指紋を取り損ねた**」状態が作れてしまう。**その状態からの保存は突き合わせる相手を持たない——つまり黙って上書きする。****型で、その状態を作れなくした**
2. **`write_file(path, contents, expect)` が、突き合わせから書き込みまでを Rust 側で一続きに行う。**フロント側で「指紋を訊く」「書く」と二回に分けると、**その隙間で書き換えられた場合を取りこぼす。**`expect` を `null` にすると突き合わせない——**別名保存が通る道**であり、食い違っているときの唯一の出口なので塞げない（(b)）

**衝突は `Err` ではなく `Written::Conflict` として返す。**`Err` は「保存という操作が失敗した」ことを表す形で、フロント側では他の失敗と同じ帯になる。**ここで起きているのは失敗ではなく、予定どおりの拒否である。**見せるものも違う（三つの出口の案内）。**文字列を読み分けさせるのではなく、型で分ける。**

**増やした状態**（第 6 節が「状態は数個」を素の TypeScript を選ぶ根拠にしている以上、増えたぶんは正直に書く）:

| 名前 | 意味 |
|---|---|
| `baseDigest: string \| null` | **いまの本文が来たファイルの版。**`null` は無題・退避からの復元で、**突き合わせる相手が無いので検知も拒否もしない** |
| `externalChanged: boolean` | **外部変更をもう知らせたか。**読み直しと保存成功で倒す |
| `reloadArmedUntil: number` | **`Mod+R` の押し直しを受け付ける期限**（(d)） |

**Rust 側の常駐状態は増えていない。**スレッドもウォッチャも無く、**指紋は呼ばれたときに数えるだけである。**

**モックを作った**（2026-09-05）。実物の版面の上で、**四つの軸を別々に選んで組み合わせられる。マウスは要らない**: https://claude.ai/code/artifact/554326df-9610-4503-9993-916e3d10adfc

**初版のモックは軸を取り違えていた。**見せ方の 5 案だけを並べ、**「中央固定」をその一案として混ぜていた。**本人の指摘（2026-09-05）:

> ルーラーを表示したとき、**スクロールとトラッカーの移動という二種類の動作が必要になり、これらをどう融合するかも設計の一部になります。**

**これが設計の本体である。**トラッカーを入れた瞬間、**画面には位置を指すものが二つになる**——**視界（スクロール）**と、**読んでいる行（トラッカー）**。帯か罫線かは表面であり、**二つをどう結ぶかが決まらなければ、見せ方は決められない。**「中央固定」は見せ方ではなく、**二つを一つに融合してしまう案**である。

**軸 1——連動（二つの位置をどう結ぶか）。**

| 案 | 動き | 得るもの | 失うもの |
|---|---|---|---|
| **A. 独立（ずれたまま）** | `↑↓` はトラッカーだけ、ホイールは視界だけ。画面外でも構わず動く | スクロールが勝手に動かない | **見えない場所に状態が残る。**動かしている実感が無い |
| **B. 独立＋引き戻し** | 同じ。ただし**画面外のときの一度目の `↑↓` は、視界を戻すだけで動かさない** | 参照から帰るのがキー一つ | 飛び先で読み始めたいとき、一度引き戻されて邪魔になる |
| **C. 追従** | `↑↓` でトラッカーを動かし、視界は必ず付いてくる | ずれが長続きしない | **`↑↓` が実質スクロールを兼ねる。**行送りと画面送りが分けられない |
| **D. 中央固定（融合）** | トラッカー＝画面の中央。ホイールでもトラッカーが動く | 状態が増えない。ずれの概念が無い | **参照の往復が原理的にできない** |

**A と D が、本人の言う原案の二つである**（「別のキーに割り当てる案」と「中央固定する案」）。**B と C はその間にある。**

**B は、gera に既にある作法の使い回しである。**未保存のまま `Mod+R` を押したとき、一度目は帯を出して止め、5 秒以内の二度目で実行する（9-6 の (d)）。**「一度目は状態を確かめさせ、二度目で動かす」は既に一度覚えてもらっている作法なので、二例目は覚える概念を増やさない**（第 4 節の第二優先）。

**引き戻しと拾い直しは、別の操作である。**離れた状態から戻る道は二つあり、**目的が違うので片方だけでは足りない。**

- **視界をトラッカーへ引き戻す**——元いた場所へ帰る。**取り返しがつく**（トラッカーは動かない）
- **トラッカーを視界へ拾い直す**——いま見ている場所から読み始める。**元の位置は失われる**

**どちらもキーに載せる。**初版のモックは後者をクリックに置いていたが、**それは誤りである**（本人の指摘、2026-09-05）——**ここまでの操作がすべてキーで完結している以上**（第 9 節、`F1` の一覧）、**片方だけをマウスに載せると、その一手のためだけに手を移すことになる。**

**拾い直しは `Enter` である。**実物の覆いの中で `Enter` は既に「決める」を意味しており（`keys.ts` の `GROUPS`）、**同じ意味を使い回すなら覚える概念は増えない**（第 4 節の第二優先）。**置く先は画面の先頭行**——「これから読む行」であって、中央では位置が予測しにくい。

**そして、キーの配分そのものが設計判断になった。**

**ずれていること自体を見せる必要がある。**二本立てにした代償は、**見えない場所に状態があること**である。**隠すと、利用者は自分がどちらを動かしているのか分からなくなる。**モックでは画面の端に帯を出し、「トラッカーは 12 行上にある」と行数つきで示している。**常設 UI を持たない方針（第 5 節）に対しては、ずれているときだけ出る一時的な帯なので、9-7 の札より軽い。**

**軸 2——`↑↓` をどちらに渡すか。**

**キーだけで完結させる以上、視界にもキーが要る。**これが原案の「操作が煩雑」の正体である。**閲覧モードの無修飾キーは空いている**（実物が押さえているのは `Mod+…` 系と `F1`、覆いの中の `↑↓` `Enter` `Esc` だけ）。**ただし編集モードでは無修飾キーが文字入力に取られるので、トラッカーは閲覧モード限定になる**——読むための道具だという位置づけの帰結であり、制限ではない。

| 配分 | トラッカー | 視界 | 代償 |
|---|---|---|---|
| **X. `↑↓` をトラッカーに渡す** | `↑↓` | `PageUp` / `PageDown` / `Space` | **一行スクロールが消える**（A・B と組んだとき。C なら `↑↓` が実質そのまま行スクロールになるので失わない） |
| **Y. `↑↓` は視界のまま** | `j` / `k` | `↑↓`（従来どおり） | **覚えるキーが増える。**`j`/`k` は vim の綴りで、**知らない利用者には手掛かりが無い**——友人がこれに当たる（第 3 節） |

**`Mod+↑↓` は採らない。**綴りは自明だが、**読書中ずっと修飾キーを押し続けることになる。**

**軸 3——`Mod+Shift+O` で飛んだとき、トラッカーはどうなるか。**

**同じ操作に目的が二つある。**参照（第 3 章を確かめて戻る）と、移動（飛び先から読み始める）。**操作の側から区別できない以上、どちらかを既定に決めるしかない。**

| 案 | 既定の読み | 代償 |
|---|---|---|
| **1. 視界だけ飛ぶ**（トラッカーは残る） | ジャンプ＝参照 | 飛び先で読み始めるとき、一手（`Enter`）が要る |
| **2. トラッカーも連れて行く** | ジャンプ＝移動 | **元いた位置が失われる。**戻り先を憶える仕組みが要る＝機能がもう一つ増える |

**gera の前例に従えば 1 である**——**取り返しがつく側を既定にする**（第 11 節、9-6）。残した位置はいつでも捨てられるが、失った位置は戻らない。**さらに 1 は規則が一つで済む**——**トラッカーが動くのは、トラッカーのキーと `Enter` のときだけ。****この規則は `Mod+F`（検索）・`Mod+R`（再読み込み）・`Mod+E`（モード切り替え）にもそのまま効く。**軸 3 は見出しジャンプだけの問題ではない。

**軸 4——見せ方。**帯／窓（上下を沈める）／段落フォーカス／罫線／帯＋減光の五つ。**軸 1 が決まらないうちは選べない**が、実装の費用はどれも描画層の差でしかない。**段落フォーカスだけは寸法をまったく測らない**（gera は段落を要素として持ち `data-line` も付けてある）ので、五つで最も安い。

**モックを作る過程で分かった、実装に効く事実が四つある。**

1. **「行」に対応する要素は存在しない。**Markdown を描いたあとの段落は一つの要素であり、その中の一行を指す要素は無い。**したがって「他の行を薄くする」は要素の色では実現できず、上に覆いを重ねるしかない。****行の矩形そのものは `Range.getClientRects()` が返す**——呼び出しはブロックごとに一回で、返るのが行ボックスの一覧である
2. **トラッカーの位置は、gera が自分で憶えなければならない状態である。**視界（`scrollTop`）はブラウザが持っているが、**トラッカーは持ってくれない。**軸 1 の費用の本体はここにあり、見せ方（軸 4）の費用よりはるかに重い
3. **段落フォーカス（軸 4）だけが、寸法をまったく測らない。**本文全体を `--dim` にして現在の段落だけ `--fg` に戻せばよく、CSS のクラス一つで済む

## 11. 設計上の規則

### 規則 1: gera は Markdown ビューアであって、LaTeX ビューアではない

本人の言:「あんまり本格的にサポートすると LaTeX 専用ビューアーになっちゃうので」「**VSCode のプラグインぐらいのサポートでいいですよ**」。

**数式を描くのは Markdown に数式が入っているからであって、LaTeX を描くためではない。迷ったら「VS Code の Markdown プレビューがやるか」を基準にする。**この規則により、定理環境・`\ref` の解決・`::: theorem` 記法などは自動的に対象外になる。

補足として事実を一つ置く。本人の文書には `\begin{theorem}` 等が 200 箇所以上あるが、それらは `STYLE.md` の中で **Markdown → LaTeX 変換規約を説明する表**に現れるものであり、本文の記法は `::: theorem T-0052` という別のものである（VS Code でも描画されない）。

### 規則 2: 一回の変更は、レビューできる大きさに収める

本人が初版を「ドシンプルに」としていた理由は、製品思想ではなく**レビューの負担**だった。本人の言:「実装が複雑になってレビューするのが大変かなーと思って、まずはドシンプルに、という会話をした気がします」。

**したがって答えは「機能を減らす」ではなく「一回の変更を小さくする」である。探す道具（アウトライン・検索。9-2）を諦める必要はない。**

### 規則 3: Claude Code 固有のものを作らない

本人は別の AI ツールに移る可能性がある（第 2 節）。**特定のツールの出力形式やディレクトリ構造に依存した仕組みを入れない。**
