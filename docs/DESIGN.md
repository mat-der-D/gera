# 設計メモ — 軽量 Markdown エディタ

作成: 2026-09-02 / 状態: 検討中（実装未着手）

## 1. 何を作るのか

AI が生成した Markdown 文書を、読んで、直して、書き戻すためのデスクトップアプリ。

汎用の Markdown エディタではない。白紙から書き始める用途は想定しない。既に存在する長い文書を通読し、冗長な部分を削り、構造を整えることに最適化する。

主な言語は日本語。利用者は一人（開発者本人）である。

## 2. なぜ既存製品では足りないか

Typora、Obsidian、Zettlr などはいずれも「自分で書く人」向けに設計されている。そのため機能の重心が執筆側にあり、次の性質を満たさない。

- 読む時間が書く時間より長いこと
- 主な操作が追加ではなく削除と並べ替えであること
- ファイルを開くのではなく、貼り付けから始まることが多いこと

この用途を正面から狙っている製品は見当たらない。ここが企画の立脚点である。

## 3. 「軽量」の定義

本プロジェクトにおける軽量とは、バイナリサイズや起動速度ではなく、**覚えるべき概念が少ないこと**を指す。設定画面をほとんど持たず、ボールトやワークスペースといった中間概念を導入しない。

サイズと起動速度は Tauri を選ぶことで副次的に得られるが、目的ではない。

## 4. 中心となる設計判断：二つのモード

同一画面で切り替える。別ウィンドウや左右分割は採らない。

### 閲覧モード（読み専用）

Markdown を HTML に変換して完全に描画する。表は表として、画像は画像として、Mermaid は図として表示する。カーソルが存在しないため、編集との整合を考える必要がなく、実装は単純な変換処理で済む。

### 編集モード

CodeMirror 6 上で、記号を残したまま装飾のみを当てる。見出しは大きく、太字は太く、引用には縦線を引く。表や画像は描画せず、Markdown の記法のまま扱う。

閲覧モードほどリッチではないが、素の Markdown よりは明確に読みやすい状態を保つ。

### なぜこの分割が有効か

リッチ表示の実装コストのほとんどは、「編集中であること」に由来する。カーソルがブロックに入ったときの復帰、選択範囲がブロックを跨ぐ場合、コピー&ペースト時の対応関係——これらはすべて編集文脈でのみ発生する。

読み専用に限定すれば、これらは消える。最も難しい表現を、最も易しい文脈だけで実装できる。

## 5. 画面構成：クロームを持たない

本文以外の常設 UI を置かない。ツールバー、サイドバー、ステータスバー、タブのいずれも持たない。ウィンドウの中身は文書だけである。

モードの切り替えはキーボード（`Cmd+E`）で行う。

### 検討した三案

比較用のモックを作成し、次の三案を同一文書で並べた。

| 案 | 構成 | 判断 |
|---|---|---|
| ミニマル | 本文のみ | **採用** |
| アウトライン常設 | 左に見出しツリー | 見送り。第 10 節に条件付きで残す |
| 査読レイアウト | 上部にツールバー | 見送り。差分ビューを初版に入れる場合のみ |

### なぜミニマルを採るか

**拡張は起きるが、縮小は起きない。**ミニマルからツールバーやサイドバーを足すことは後からできるが、一度置いた UI が減ることは実際にはない。可逆な方向から始める。

加えて、実装量が三案で最も小さく、第 9 節の順序 1 と 2 だけで完成する。

### モードの状態を、本文の書体で示す

閲覧モードは明朝（Noto Serif JP）、編集モードはゴシック（Noto Sans JP）で組む。

これは装飾ではなく、常設 UI を持たないための手段である。モードの状態を表示するインジケータを別に設けなくても、本文そのものが現在の状態を示す。長い日本語を読むのは明朝、直すのはゴシックという読み書きの慣習にも沿う。

**この判断が成立しなければ、ミニマル案は成立しない。**状態が分からなければ、状態表示のための UI が必要になり、それは案 3 である。実装後、最初に検証すべき点はここである。

### 認識している弱点

AI が生成する文書は 3000 字を超えることが多く、**本文だけでは現在位置が分からなくなる。**第 10 節のアウトライン表示は、この弱点への対処として残してある。

## 6. 日本語 IME への対応

編集モードで記号の出し入れを行う際、**カーソルのある行は常に生の Markdown を表示する**という規則を置く。

変換中はカーソルが必ずその行にあるため、変換途中で装飾処理が走ることがない。IME による表示崩れを、機能ではなく規則によって回避する。

これは Obsidian のライブプレビューが採る方式と同じ考え方である。

## 7. 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| アプリ基盤 | Tauri | 配布サイズと起動速度。Rust の記述量は少ない |
| エディタコア | CodeMirror 6 | IME の実用水準での対応。ビューポート仮想化。装飾機構 |
| フロントエンド | TypeScript | ロジックの大半はここに置く |
| Rust 側の責務 | ファイル入出力、ダイアログ、ウィンドウ状態の保存のみ | 200 行程度を想定 |

### エディタコアを自作しない

カーソル移動、選択、アンドゥ、IME、折り返しの実装だけで数ヶ月かかる。CodeMirror 6 を土台とすることが唯一の現実解である。

### 性能について

CodeMirror 6 は画面に見えている行だけを DOM 化するため、文書全体の長さは描画コストに影響しない。Lezer パーサが構文木を差分更新するため、全文の再パースも発生しない。

装飾の追加が性能問題を引き起こすとは想定していない。

## 8. 作らないもの

以下は明示的に実装しない。導入した時点で第 3 節の定義が破綻する。

- フォルダツリー、ボールト、タグ、バックリンク
- プラグイン機構、テーマ機構
- 同期、クラウド連携
- 編集モードでの表の WYSIWYG 編集
- 編集モードでの数式・Mermaid のライブ描画（閲覧モードでのみ描画する）

## 9. 実装の順序

1. **編集モードの装飾（記号は常に表示）とファイル入出力**
   この時点で実用になる。
2. **閲覧モード（完全描画・読み専用）**
   ビューアとしての価値はここで出揃う。
3. **編集モードでの記号の出し入れ（カーソル行は生）**
   編集の快適さはここで得られる。最も壊れやすいため、土台が固まってから着手する。
4. **アウトライン移動と整形機能**

順序 3 を後回しにしているのは意図的である。効果は大きいが破損リスクも高く、1 と 2 だけでも用途は満たせる。

## 10. 検討済みだが先送りする機能

### 差分ビュー

文書を開いた（貼り付けた）時点をベースラインとして保持し、自分が加えた変更を差分表示する。

AI 出力の査読において効果が最も大きいと考えられるが、実装量が上記 1〜3 の合計を超える見込みのため、次のバージョンに回す。

### 整形のワンショット

AI 出力に頻出する乱れを一括で修正する。

- 全角空白の混入
- 箇条書き記号の不統一（`-` と `*` の混在）
- 見出しレベルの飛び（h2 の次に h4 が来る）
- 末尾の余分な空行

### 日本語の校正支援

「である」と「ですます」の混在、二重助詞、句読点の不統一。意味の判定を伴うものは難しいため、機械的に検出できる範囲に限定する。

### アウトライン表示（閲覧モード限定）

第 5 節で見送ったアウトラインを、**閲覧モードでのみ**表示する折衷案。

読んでいるときに現在位置が要るのであって、書いているときには要らない。編集モードでは出さないため、本文の幅が狭くなる問題も、常設 UI が増える問題も回避できる。

第 5 節で認識した弱点への対処としては、これが最も安い。長い文書を扱って実際に困った時点で着手する。

## 11. 未決の論点

- **編集結果の戻し先。** ファイルとして保存するのか、クリップボードへ戻して AI との対話に貼り直すのか。後者のみであれば「保存」という概念自体を持たない設計が可能になり、さらに軽くなる。実際の作業の流れを観察してから決める。
- **署名と配布。** 自分だけで使ううちは不要。他者へ配布する段階で、macOS と Windows の署名について費用と手間を見積もる必要がある。
- **フロントエンドのフレームワーク。** 素の TypeScript + Vite で足りるか、React などを入れるか。画面は本文一枚、状態はモードとファイルパス程度で、DOM は CodeMirror が管理する。現時点の推奨は素の TypeScript。
- **閲覧モードの Markdown → HTML 変換。** `markdown-it` を使うか、CodeMirror が内部に持つ Lezer の構文木を流用して変換器を一つに寄せるか。後者は HTML 化を自前で書く必要がある。初版の推奨は `markdown-it`。
