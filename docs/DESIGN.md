## 1. 何を作るのか

AI が生成した Markdown 文書を、読んで、直して、書き戻すためのデスクトップアプリ。

汎用の Markdown エディタではない。白紙から書き始める用途は想定しない。既に存在する長い文書を通読し、冗長な部分を削り、構造を整えることに最適化する。

主な言語は日本語。**作るのは開発者一人だが、利用者は開発者と友人の二人である。**

**メインの用途は、AI が出力した Markdown を読むことである**（第 2 節）。直しと書き戻しはその延長にある。

開発機は Linux（Ubuntu 24.04）、**友人への配布先として想定するのは Windows。**

利用者が本人だけではない以上、**配布と署名は設計の範囲内にある**（第 12 節）。一方で開発は一人であり、複数人での開発を前提とした仕組み（レビュー、ブランチ運用）は導入しない。

## 2. なぜ既存製品では足りないか

Typora、Obsidian、Zettlr などはいずれも「自分で書く人」向けに設計されている。そのため機能の重心が執筆側にあり、次の性質を満たさない。

- 読む時間が書く時間より長いこと
- 主な操作が追加ではなく削除と並べ替えであること
- ファイルを開くのではなく、貼り付けから始まることが多いこと

この用途を正面から狙っている製品は見当たらない。ここが企画の立脚点である。

## 3. 速度を第一に置く

**本プロジェクトの優先順位は、第一に起動速度と動作速度、第二にシンプルさである。**

1. **起動速度**——第一優先。開いた瞬間に読み始められること
2. **動作速度**——同じく第一優先。打鍵、スクロール、モードの切り替えが待たされないこと
3. **シンプルさ**——二番目。**覚えるべき概念が少ないこと**を指す。設定画面をほとんど持たず、ボールトやワークスペースといった中間概念を導入しない

**順序に意味がある。**シンプルさは価値だが、速度と衝突したときに優先されるのは速度である。逆に、速度を保つ手段としてシンプルさが効く場面は多い——機能を足せば起動も動作も重くなるため、二つは多くの場合同じ方向を向く。

## 4. 中心となる設計判断：二つのモード

同一画面で切り替える。別ウィンドウや左右分割は採らない。

### 閲覧モード（読み専用）

Markdown を HTML に変換して完全に描画する。表は表として、画像は画像として、Mermaid は図として表示する。カーソルが存在しないため、編集との整合を考える必要がなく、実装は単純な変換処理で済む。

### 編集モード

CodeMirror 6 上で、記号を残したまま装飾のみを当てる。見出しは大きく、太字は太く、引用には縦線を引く。表や画像は描画せず、Markdown の記法のまま扱う。

閲覧モードほどリッチではないが、素の Markdown よりは明確に読みやすい状態を保つ。

### なぜこの分割が有効か

リッチ表示の実装コストのほとんどは、「編集中であること」に由来する。カーソルがブロックに入ったときの復帰、選択範囲がブロックを跨ぐ場合、コピー&ペースト時の対応関係——これらはすべて編集文脈でのみ発生する。

読み専用に限定すれば、これらは消える。最も難しい表現を、最も易しい文脈だけで実装できる。

## 5. 画面構成：最も簡素な案から始める

**初版は、本文以外の常設 UI を置かない構成で作る。**ツールバー、サイドバー、ステータスバー、タブのいずれも初版には持たせない。ウィンドウの中身は文書だけである。

**これは出発点の選択であって、恒久的な禁止ではない。**初版を使ったうえで必要と分かった常設 UI は、後から足す。

モードの切り替えはキーボード（`Mod+E`）で行う。CodeMirror の `Mod-` 接頭辞は macOS で `Cmd`、Linux と Windows で `Ctrl` に解決されるため、プラットフォームごとの分岐を書かない。

### 検討した三案

| 案 | 構成 | 判断 |
|---|---|---|
| ミニマル | 本文のみ | **採用**（初版の出発点として） |

### なぜミニマルから始めるか

**足していく前提で、足しやすい側から始める。**ミニマルからツールバーやサイドバーを足すことは後からできるが、一度置いた UI を減らすのは実際には難しい。**可逆な方向から始める。**

これは「増やさない」という主張ではない。**増やす判断を、実物を使ってから下せるようにするための順序である。**

加えて、実装量が三案で最も小さく、第 9 節の順序 1 と 2 だけで完成する。

### モードの状態を、本文の書体で示す

閲覧モードは明朝、編集モードはゴシックで組む。**配布先の OS ごとに実在する書体が違うため、単一のファミリー名ではなくスタックで指定する。**

| | スタック |
|---|---|
| 明朝（閲覧） | `"Noto Serif CJK JP", "Yu Mincho", YuMincho, "Hiragino Mincho ProN", serif` |
| ゴシック（編集） | `"Noto Sans CJK JP", "Yu Gothic", YuGothic, "Hiragino Sans", sans-serif` |

**Windows には Noto CJK が標準で入っていない。**代わりに游明朝・游ゴシックが Windows 8.1 以降に標準搭載されており、明朝とゴシックの対比はこれで保てる。**フォントは同梱しない**（Noto CJK は OFL なので同梱自体は可能だが、1 書体十数 MB になり、得られるものに対して高い）。

Linux 側ではファミリー名に `CJK` が入る点に注意する。Ubuntu が `fonts-noto-cjk` で提供するのはこの名前で、`Noto Serif JP`（CJK なし）は**別のファミリーであり標準では存在しない。**

**誤った名前だけを書くと黙って fallback し、両モードが同じ書体で組まれて、この節の要が無言で失われる。**スタックで書いたうえで、起動時に実際に解決できたかを測り、失敗したら log に出す。

これは装飾ではなく、初版で常設 UI を置かないための手段である。モードの状態を表示するインジケータを別に設けなくても、本文そのものが現在の状態を示す。長い日本語を読むのは明朝、直すのはゴシックという読み書きの慣習にも沿う。

**この判断が成立しなければ、ミニマル案は成立しない。**状態が分からなければ、状態表示のための UI が必要になり、それは案 3 である。実装後、最初に検証すべき点はここである。

## 6. 日本語 IME への対応

編集モードでは、**カーソルのある行は常に生の Markdown を表示する**という規則を置く。これは Obsidian のライブプレビューと同じ方式である。

### この規則の根拠（2026-09-02 訂正）

当初この規則は「IME の表示崩れを回避するため」と書いていた。**これは誤りだった。**

CodeMirror 6 は 6.15.3 で、変換中の DOM 保護を**装飾より下の描画層**に移している。変換範囲を覆う view object を固定表現に差し替える実装であり、装飾が composition を壊すことはない。**IME 対策としてこの規則は不要である。**

規則は残す。ただし根拠は**「作業中の行では記法を見て、直接触る必要がある」**——編集容易性である。

**根拠を取り違えたままにしない。**IME が平気だと分かった時点でこの規則を捨てると、編集容易性を失う。捨ててよい理由と、残すべき理由は別のものである。

### 実測（2026-09-02、開発機）

Ubuntu 24.04 / GNOME Wayland / ibus + mozc / webkit2gtk-4.1 2.52.6。Tauri と同一エンジンの `MiniBrowser` 上で、CodeMirror 6 ＋ 装飾 ＋ 本節の規則を再現して計測した。対照群として素の `textarea` を並べた。

| 症状 | 原因 | 対処 |
|---|---|---|
| 未確定文字の下線が数文字ずれる | `GTK_IM_MODULE` が空で、GTK3 が ibus モジュールを経由していなかった | **`GTK_IM_MODULE=ibus` で解消。**下記の通りアプリ側で設定する |
| 変換候補窓が文字の右下にずれる | [WebKit bug 218148](https://bugs.webkit.org/show_bug.cgi?id=218148)。preedit 中に `absoluteCaretBounds()` が空矩形を返し、`gtk_im_context_set_cursor_location()` に正しい位置が渡らない | **回避不能。**数年来未修正。候補窓を描くのは ibus でアプリ外のため、JS からも触れない |

**素の `textarea` と CodeMirror + 装飾で挙動は完全に一致した。**CodeMirror・装飾・本節の規則はいずれも無関係である。

**候補窓のずれは、Tauri を採る代償として受け入れる**（第 7 節）。インライン入力そのものは正常で、文字は正しく入る。VS Code（Electron/Chromium）では再現しないため、これは WebKitGTK 固有の欠陥である。

### この欠陥は Linux にしか出ない

Tauri は OS 標準の webview を使うため、**エンジンがプラットフォームごとに違う。**

| OS | エンジン | 候補窓のずれ |
|---|---|---|
| Linux | WebKitGTK | **出る**（bug 218148） |
| Windows | WebView2（Chromium） | 出ない |
| macOS | WKWebView | 出ない |

**配布先として想定している Windows では起きない**（第 1 節）。したがってこの欠陥を踏むのは開発機の Linux だけであり、**友人には影響しない。**

### 起動時に `GTK_IM_MODULE` を設定する

Linux では GTK の初期化前に環境変数を設定する。Tauri の `main()` の先頭、`tauri::Builder` に触れる前に置く。

**ibus 決め打ちにしない。**動いている IME デーモンを見て決め、既に値が入っているなら**上書きしない**（利用者の設定を壊さないため）。

## 7. 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| アプリ基盤 | **Tauri 2**（2.11 系） | 配布サイズと起動速度。Rust の記述量は少ない |
| エディタコア | **CodeMirror 6** | IME の実用水準での対応。ビューポート仮想化。装飾機構 |
| フロントエンド | **素の TypeScript + Vite**（フレームワークなし） | 下記 |
| 閲覧モードの変換 | **`markdown-it` + DOMPurify** | 下記 |
| Rust 側の責務 | ファイル入出力、ダイアログ、ウィンドウ状態の保存のみ | 200 行程度を想定。呼び出しは `src/host.ts` に集約する |

### フレームワークを入れない

画面は本文一枚しかなく、DOM は CodeMirror が所有する。持つ状態はモード・ファイルパス・dirty・差分用ベースラインの 4 つだけである。

**React の価値は、状態に対してコンポーネント木を突き合わせることにあるが、突き合わせる木がない。**むしろ CodeMirror 6 は DOM を命令的に保持するため、React 側では ref とエフェクトで `EditorView` の再生成を防ぐ手当てが要る。これは利益ではなく摩擦である。

そして第 3 節の第二優先であるシンプルさから見ても、フレームワークの導入は**覚えるべき概念を増やす**側の変更である。ランタイムを一つ増やす以上、第一優先の起動速度にも効く。

### 変換器を一つに寄せない

`@lezer/markdown`（CodeMirror が内部で使う）を閲覧モードにも流用する案を検討し、**採らない。**

理由は二つある。第一に、`@lezer/markdown` は Lezer 構文木を出すだけで、**HTML 描画器を持たない。**自前で書くとは、全ノード種の走査・インライン装飾・実体参照エスケープ・リンク解決・リストの tight/loose 判定を書くことである。

第二に、寄せたい動機そのものが成立しない。**寄せる目的は両モードの表示一致だが、編集モードは記法をその場で装飾し、閲覧モードは描画する——両者に突き合わせるべき対応関係が存在しない。**存在しない問題のために数週間を払う形になる。

### 閲覧モードの HTML は必ず sanitize する

AI 出力の Markdown を HTML 化して webview で描くと、`<script>` ひとつで第 7 節が Rust に与えたファイル入出力コマンドに到達する。**閲覧モードの描画経路は、そのまま攻撃面である。**

`markdown-it` を `html: true` で使い、**描画前に必ず DOMPurify を通す。**

`html: false`（生 HTML をエスケープ）でも安全にはなるが、AI 出力に頻出する `<details>` や `<br>` が生テキストとして出てしまい、査読の役に立たない。**安全性は sanitize で確保し、表現力は落とさない。**

Tauri 側の capability も、実際に使うコマンドだけに絞る。

### Tauri を降ろさなかった理由

第 6 節の実測で、**変換候補窓のずれは WebKitGTK 固有かつ修正不能**と確定した。Electron（Chromium）なら起きない。

**それでも Tauri を採る。理由は第 3 節の優先順位である。****起動速度と動作速度が第一優先である以上、Tauri の小さいバイナリと速い起動は副次的な効能ではなく目的そのものであり、Electron は候補にならない。**Electron は Chromium ランタイムを丸ごと同梱するため配布サイズが 150MB 前後になり、起動も重い。**乗り換え先が第一優先に正面から反するのだから、比較検討の余地はない。**

残った欠陥は候補窓の位置だけで、インライン入力は正常に働き、文字は正しく入る。**見た目の問題であって、機能の問題ではない。**

さらに、**この欠陥は Linux にしか出ない**（第 6 節）。Tauri が OS 標準の webview を使う結果、Windows では WebView2（Chromium）が動く。**配布先の Windows では、そもそも再現しない。**

加えて、Electron へ移れば Rust の 200 行と一緒に別の概念（main/renderer の分離、preload、contextIsolation）が入ってくる。**第 3 節の第二優先であるシンプルさも同時に損なう。**速度とシンプルさの両方を明け渡して得られるのが候補窓の位置だけなら、取引として成立しない。

なお、乗り換えが必要になった場合に書き直す対象は `src/host.ts` の 5 本だけである。そのために抽象化の層を設けることはしない（実装が一つしかない層は、それ自体が概念を一つ増やす）。**呼び出しを一箇所に集めておけば足りる。**

### エディタコアを自作しない

カーソル移動、選択、アンドゥ、IME、折り返しの実装だけで数ヶ月かかる。CodeMirror 6 を土台とすることが唯一の現実解である。

### 性能は想定せず、測る

CodeMirror 6 は画面に見えている行だけを DOM 化するため、文書全体の長さは描画コストに影響しない。Lezer パーサが構文木を差分更新するため、全文の再パースも発生しない。**仕組みの上では装飾の追加が性能問題を引き起こす理由はない。**

**しかし、速度が第一優先である以上（第 3 節）、「想定していない」で済ませない。測る。**

測る対象は三つである。

- **(a) 起動から編集可能になるまでの時間**——プロセス起動、webview の初期化、CodeMirror のマウントを含む実時間
- **(b) 打鍵から画面に出るまでの遅延**——特に**日本語 IME の変換中**。preedit の更新ごとに装飾の再計算が走る経路であり、最も遅くなりやすい
- **(c) 長い文書を開いたときの初回描画**——AI 出力は 3000 字超が普通であり、これを基準の長さとする

**これらは「気になったら見る」ではなく、初版の受け入れ条件である。**実装順序 1（第 9 節）が動いた時点で測り、数値を第 12 節に記す。仕組みの説明は根拠であって、測定の代わりにはならない。

## 8. 初版では作らないもの

以下は初版のスコープから外す。**これは初版を小さく保ち、まず動くものを手に入れるための除外であって、恒久的な禁止ではない。**初版を使ったうえで必要だと分かったものは、後から作りうる。

**外す理由は共通している。**いずれも初版の用途——AI が出力した Markdown を読み、直し、書き戻す——に無くても成立し、かつ実装量が第 9 節の順序 1〜3 に匹敵するか、それを超える。**先に動くものを得て、それから判断する。**

もう一つ理由がある。**機能を足せば起動も動作も重くなる。**第 3 節の第一優先は速度であり、初版で機能を絞ることは、速度の基準線を先に確保することでもある。**後から足すときは、第 7 節の (a)(b)(c) を測り直したうえで足す。**

- フォルダツリー、ボールト、タグ、バックリンク
- プラグイン機構、テーマ機構
- 同期、クラウド連携
- 編集モードでの表の WYSIWYG 編集
- 編集モードでの数式・Mermaid のライブ描画（初版では閲覧モードでのみ描画する）

これらを後から足す場合、第 3 節の優先順位に照らして判断する。**速度（第一）を落とすなら足さない。シンプルさ（第二）だけを理由に却下はしない**——覚えるべき概念が一つ増えることは、実際に必要だと分かった機能を退ける決め手にはならない。

## 9. 実装の順序

1. **編集モードの装飾（記号は常に表示）と入出力**
   ファイルの開く／保存、クリップボードへの全文出力、不可視の自動退避（第 11 節）。この時点で実用になる。
2. **閲覧モード（完全描画・読み専用）**
   ビューアとしての価値はここで出揃う。
3. **編集モードでの記号の出し入れ（カーソル行は生）**
   編集の快適さはここで得られる。最も壊れやすいため、土台が固まってから着手する。
4. **アウトライン移動と整形機能**

順序 3 を後回しにしているのは意図的である。効果は大きいが破損リスクも高く、1 と 2 だけでも用途は満たせる。

## 10. 検討済みだが先送りする機能

### 差分ビュー

文書を開いた（貼り付けた）時点をベースラインとして保持し、自分が加えた変更を差分表示する。

AI 出力の査読において効果が最も大きいと考えられるが、実装量が上記 1〜3 の合計を超える見込みのため、次のバージョンに回す。

### 整形のワンショット

AI 出力に頻出する乱れを一括で修正する。

- 全角空白の混入
- 箇条書き記号の不統一（`-` と `*` の混在）
- 見出しレベルの飛び（h2 の次に h4 が来る）
- 末尾の余分な空行

### 日本語の校正支援

「である」と「ですます」の混在、二重助詞、句読点の不統一。意味の判定を伴うものは難しいため、機械的に検出できる範囲に限定する。

### アウトライン表示（閲覧モード限定）

第 5 節で見送ったアウトラインを、**閲覧モードでのみ**表示する折衷案。

読んでいるときに現在位置が要るのであって、書いているときには要らない。編集モードでは出さないため、本文の幅が狭くなる問題も、常設 UI が増える問題も回避できる。

第 5 節で認識した弱点への対処としては、これが最も安い。長い文書を扱って実際に困った時点で着手する。

## 11. 決定事項（2026-09-02）

### 編集結果の戻し先 → ファイル入出力を維持し、クリップボード出力を足す

「実際の作業の流れを観察してから決める」としていたが、**これは実装順序 1 の中身そのもので、先送りのままでは着手できない。**

観察を待つ必要はなかった。**この先送りは「間違えると高くつく」という前提で置かれていたが、実際には両方を満たすほうが安い。**第 7 節と第 9 節は既にファイル入出力を確約しており、そこへクリップボードへの一括コピーを足す費用は数行である。

「保存という概念を持たない設計」は、**クリップボードが唯一の経路である場合にのみ**成立するが、それを支持する材料がない。この設計文書自体が gera の対象そのものでありながら、ファイルとして git に置かれている。

さらに、**概念と機構を分ける。**「保存」という**概念**を UI に出さないことと、バッファを継続的に退避する**機構**を持つことは両立する。3000 字超を編集中に落ちて全部消える経路を、コマンドを増やさずに塞げる。

- ファイルを開く／保存する（`Mod+O` / `Mod+S`）
- 全文をクリップボードへ出す（`Mod+Shift+C`）
- 不可視の自動退避をアプリ専用領域に置く。**UI には出さない**
